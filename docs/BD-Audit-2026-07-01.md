## Verdict

The module is **architecturally sound and operationally healthy**. The pursuit-lifecycle write path
(grab / reassign) is the best-engineered SQL in the codebase — guarded single transactions with
`XACT_ABORT` + `@@ROWCOUNT` gates that the auditors explicitly called out as "the pattern the rest of the
codebase should copy." DI wiring is complete (zero missing registrations), binding integrity is clean
(zero silent binding failures on audited views), CancellationToken hygiene is near-perfect, enum/int-literal
drift across 9 mirrored SQL sites is **zero**, live DB consistency is excellent (0 duplicate engagements,
0 orphaned audit rows, coherent claim states except one legacy row), and the Worker is green
(120+ ingestion streams on cadence, near-zero failure rates).

The risk is concentrated in four places: **(1)** an unguarded async-void crash family in the Fee Proposal
window, **(2)** a latent-but-real data-loss defect in the ingestion pipeline plus intel-persist failures that
vanish into a listenerless `Trace`, **(3)** zero automated tests on the entire lifecycle write path, and
**(4)** the already-known committed credentials plus a fully trust-based authorization model.

## Findings — Critical

### C1. Fee Proposal window: unguarded async-void family → app crash on store failure ⚠ VERIFIED
`Kor.Operations.App\FeeProposal\FeeProposalBuilderWindow.xaml.cs:40-43, 82-86, 88-96, 98-103, 150, 178, 350-359`
`SaveProposal_Click`, `SaveProposalAs_Click`, `ManageStaff_Click`, window `Loaded`, Ctrl+S, and the save step
inside PDF/DOCX export all `await` store calls in `async void` with **no try/catch anywhere in the chain**
(the VM methods don't catch either). Any SQL timeout/outage at open or save time is an unhandled exception →
**whole-app crash** — on the Save button. Worst variant: `OnClosing` (:331-348) — "Yes, save before closing"
yields at the first await, WPF continues the close immediately, and the save races teardown; changes can be
lost while the UI said they were being saved.

### C2. Ingestion partial-failure permanently drops opportunities (latent — 0 occurrences live) ⚠ VERIFIED code + live
`Kor.Opportunities.Data\Ingestion\IngestionService.cs:233-258` (mirrored in the historical path)
Observation insert → opportunity insert → link are three statements, no transaction. If the opportunity INSERT
throws after the observation row commits, every later run hits the observation's unique content-hash, sees
"duplicate," checks `GetByKeyAsync` — and when the opportunity does *not* exist, still returns `Duplicate`
**without repairing**. The candidate is silently unrecoverable while its source content stays byte-identical.
**Live check: 1,485/1,485 active observations are linked — it has never fired.** Real design flaw, zero damage
to date; the repair is cheap (create-when-missing on the duplicate path).

### C3. Committed credentials (pre-existing, previously flagged — rotation owner: Ian) ⚠ KNOWN
- `set-filesync-env.ps1` / `set-filesync-env-server.ps1` (git-tracked): Graph client secret + SQL user/password.
- `_Scripts Rebuild\FileSync\Production\*.ps1` — 14 tracked files repeating the same Graph secret.
- `EmailFiler\EmailFilerv2\app.config` + `EmailFilerRibbon.cs`: SQL credentials in tracked config/source.
- `.claude\settings.local.json` (NOT tracked, on disk): BC Bid + Bids&Tenders portal passwords embedded in
  allowlist command strings.
Not new this audit; listed for completeness. Everything BD-new uses env-vars correctly (worker/app configs are
clean; `OpportunitiesWorkerOptions` self-notes the DPAPI/KeyVault hardening path).

## Findings — Major

### M1. Store-returned RowVersion is stale after Insert/Update → spurious concurrency failures ⚠ VERIFIED
`Kor.Opportunities.Data\Opportunities\SqlOpportunityStore.cs:184, :238`
The OUTPUT clause captures the row (incl. `RowVersion`), then `ResolveBuyerCanonicalAsync` runs a **second
UPDATE** on the same row, bumping the rowversion behind the returned object. Whenever the buyer resolves, the
caller holds a stale `RowVersion` and the next save throws `OpportunityConcurrencyException` with no actual
conflict. Trigger requires an edit cycle that reuses the returned object without a reload.

### M2. `CrmEngagementStageHistory` is dead-on-arrival: no writers AND would truncate if written ⚠ VERIFIED (2×)
`Schema\267_PursuitLifecycleFoundation.sql:130-155`
Live table has **0 rows**; repo-wide grep confirms **nothing writes it** — stage transitions in
`SqlCrmEngagementStore.UpdateAsync`, the grab, and the proposal auto-advance record no history, so the design's
"stage age" analytics have no source. Compounding it, `ByStaffId` there is still `nvarchar(20)` — migration 270
widened every other staff column to 150 for UPNs but skipped this one; the first writer will hit the exact
truncation failure 270 was created to fix. Decide: wire writers + widen, or drop the table.

### M3. Intel-persist failures vanish into a listenerless `Trace` ⚠ agent-verified
`SqlEnrichmentTrackingStore.cs:248-263`, `IntelPersistenceService.cs:106/136/228`
The Worker logs via Serilog only; nothing wires a TraceListener. A failed intel persist (FK violation,
truncation, deadlock) is caught, "logged" to nowhere, and the enrichment is marked `ok` with the refresh pushed
out — intel silently never lands, and past the 7-day catch-up window it's unrecoverable **and undiagnosable**.

### M4. MERGE upserts without HOLDLOCK — duplicate-key race under concurrent ingestion ⚠ agent-verified
`SqlCanonicalOrgStore.cs:652-676` (`UpsertAliasAsync`), `SqlEnrichmentTrackingStore.cs:147-166`
Unlike the Intel MERGEs (which correctly use `WITH (HOLDLOCK)`), these can double-take the NOT-MATCHED branch
under the research poller's concurrency of up to 8 — either an unhandled dup-key aborts an ingestion batch or
duplicate alias rows are minted.

### M5. Zero automated tests on the entire lifecycle write path ⚠ VERIFIED inventory
Grab tx, reassign tx, stage change, attribution query, DataRetirementJob (incl. all three MPI exemptions that
fix the design's one 🔴 bug), `EnsureEngagementForAsync`, ingestion claim-preservation, dedup/purge tools —
**none have a single test**. BD test investment is concentrated almost entirely in read-side report generation
(which is well covered). The paths that mutate ownership/money data ship on manual verification alone.

### M6. Duplicate migration numbers 47/48/49 + manual-apply ambiguity ⚠ agent-verified
Two files each at numbers 47, 48, 49 (e.g. `48_BcBidMaxPagesLift` vs `48_CrmEngagementBdTracking`, where the
CRM twin creates columns that 49 and live code depend on). With no migration runner, "apply through N"
instructions are ambiguous and numeric-sort tooling would tie-break nondeterministically.

### M7. App-layer robustness cluster (BriefsMaker pickers + missing per-selection CTS) ⚠ agent-verified
- `BriefsMakerWindow.xaml.cs:121-200`: all three pickers (org/project/person) are unguarded async-void — a
  store failure on the *first user action* in that window crashes the app.
- `OpportunitiesViewModel.cs:234-235`: detail loads use `CancellationToken.None` with no per-selection CTS
  (the sanctioned pattern already exists in CrmViewModel/BdTrackingViewModel); A→B→A reselection can duplicate
  `SelectedInterestedFirms` rows and stale loads pile up while scrolling.

### M8. FeeProposalBuilderViewModel invisible to the AI ⚠ agent-verified
The only in-scope BD VM violating the firm every-VM-implements-`IAiContextProvider` rule. The fee-proposal
builder — a core pursuit surface — exposes nothing (document name, blocks, dirty state, linked pursuit).

### M9. Authorization is fully trust-based; audit identity is spoofable ⚠ agent-verified (accept or fix consciously)
Grab, reassign (incl. sending mail as the actor), stage change to Won/Lost, contact delete, and BD Admin
(run-now/enable jobs) have **no role checks** — any app user is a "manager." `ResolveActor()` falls back to the
user-editable `UserUpnOverride` then `Environment.UserName`, and every audit row trusts it. Defensible for a
LAN-only internal tool (matches KOR's model), but it should be an explicit acceptance — the design's M5 called
for role gating that was never built. Also `CrmView.ResolveActor` (:404-417) uses a different, weaker fallback
chain than Bazaar/Overwatch — same action, different identity stamping.

### M10. HTML injection in BD visual reports (WebView2) ⚠ agent-verified
`Kor.Opportunities.Data\BdReports\Generators\BdVisualHtml.cs:66, 111-117`
Client-side JS template literals inject DB-sourced org/project names (which originate from scraped external
sources) into the DOM unencoded — a hostile name executes script in the report preview. Every other HTML
generator audited (morning report, preview builder, reassign email) encodes correctly.
