## C. Does this plan stop “design, then not implement” for itself?

**FATAL — No.** A flaws document, a mapping to mechanisms, a scored inventory, and Ian's review can all be completed while the pre-check remains unwired. The plan has no owner/date/finish condition for a smallest working slice, no proof that a real job command invokes it, no deliberate bad job shown refused, and no rule that closes the existing row only after those facts are read back. “Build after packages ship” is an ordering decision, not an execution guarantee. The board already had done-whens and owed rows; the proposed change adds no stronger closure mechanism. [Brief, lines 80–90; RESET-PLAN.md, lines 1–5, 60–72; RULES-TO-CHECKS.md, lines 742–760.]

## D. Does it move fault-finding to the start?

**FATAL — It describes that move; it does not make it.** The reset's exact-set pre-check is the right starting point, but this new plan names no runnable check and no point in `virtual_drafter.py run` or its launcher that refuses the expensive stage. It also cannot promise “most faults” from an offline picture alone: Ids 109 and 113 show defects that passed a plot gate or checks sharing the writer's wrong assumption. Measure *which* historically late faults become visible before a full run, with independent expected results and the exact bytes the run will consume. **The actual command wiring and detection rate are not checked** within the seven permitted files. [RESET-PLAN.md, lines 33–49, 65–66; brief, lines 80–90; mistakes Ids 109, 113.]

## E. Is scoring guards against the mistake record valid?

**SERIOUS — Valid as a replay sample, invalid as the sole deletion rule.** For each recorded mistake, show the earliest checkpoint that could have observed its exact evidence, replay the recorded input through that checkpoint, and count a hit only if it would stop the mistake before the expensive or irreversible action. Include legitimate neighbouring actions to measure false refusals, time spent and bypasses. GUARDS-BAR already asked for known misses and real transcript false positives; RULES-TO-CHECKS shows why both matter. [GUARDS-BAR.md, lines 4–16; RULES-TO-CHECKS.md, lines 82–101, 114–123.]

“Of Ian's catches, how many would this hook have caught first?” is biased. The export contains only **11 of 115** `CaughtBy=Ian` rows; a guard that prevented a fault cannot appear as an Ian catch. Some rows record a guard *causing* harm (Id 73), a peer catching a near miss (Ids 42, 91), or a defect only an engineer could judge (Id 109). Historical replay also cannot test a new artifact shape or an unrecorded near miss. “Cut what catches none” would delete safety controls with low-frequency but severe outcomes, such as the protected-host path (Ids 21, 23) or secret import (138). Score by prevented severity and run cost as well as true/false positives; use red known-bad artifact tests, exact production-path wiring tests, and a per-job count of faults found **before** versus **after** the full run. [Mistakes export, cited Ids; HOW-WE-BUILD.md, lines 54–60.]

## G. The three smallest changes I would keep

1. **An enforced preflight inside the existing job run entry point.** Before any full Revit/ETABS/SAFE stage, the command consumes the exact model, answer key and build sha it will run, produces every available offline sheet/storey view, and refuses sha mismatch, footprint/count errors and missing look evidence. Use the already specified sample path for what offline rendering cannot prove. Demonstrate refusal on a real known-bad 31218 input and allow on its corrected input; record elapsed time and faults moved forward. **This is the first build task, not a new framework document.** [RESET-PLAN.md, lines 33–49, 65–66; mistakes Ids 84, 109, 113.]
2. **One immutable release/handoff operation on the existing package route.** It creates a fresh destination, records hashes and source sha for the exact bytes tested, looks at that exact set, checks the recipient's required outputs, and refuses overwrite, dirty staging or a missing output. Read back the destination and manifest after writing. This addresses the 13–15 Nov releases in the brief and export Ids 72, 82, 99–102; it must replace or tighten the current release route, not sit beside it. [Brief, lines 70–77; mistakes cited Ids.]
3. **A machine-checked completion condition on the existing board/review path.** A framework row cannot close as built until it names the production entry point, the old known-bad input that fails there, the corrected input that passes, and a wiring check that fails when the mechanism is removed. Require the same evidence for a proposed replacement before removing an old guard. Use GUARDS-BAR's red, false-positive and wiring standard; stop treating a cited filename or design page as completion. This specifically prevents this rebuild from ending at `FLAWS.md`. [GUARDS-BAR.md, lines 3–16; RULES-TO-CHECKS.md, lines 742–760; mistakes Ids 73, 139.]
