# Codex: KOR memory and token design

## Independent recommendation (written before reading the sealed draft)

**Keep the whole memory in KOR; put only the evidence needed for this decision into a model request.** “Know everything” should mean that a session can *find, verify, and cite* every current relevant record, including a record whose wording does not match the task. It cannot mean putting all bodies in a finite context: Operations bodies alone are estimated at 1.3 million tokens, beyond the reported 900,000-token window ([START-FULL-MEMORY](../../../Framework/docs/START-FULL-MEMORY.md)). A model that has seen every one-line description has not necessarily understood, selected, or even read the right body.

**Store.** Keep `brain.Memory`, `LaneState`, events and the board in KorStandards, with append-only supersession and source hashes. Files hold transcripts, drawings, reports and other bulk; SQL holds IDs and pointers. Add a *versioned retrieval view*, not another brain: module, type, status, subject aliases, exact names/paths, source hash, dependency and contradiction links, and a short abstract for each record. Maintain a complete manifest with `X of Y` counts and hashes. Recheck changed sources and expose stale/contradictory records explicitly; never quietly turn an old claim into a current one. Existing code and tests remain the strongest form of executable memory ([KNOWLEDGE-IDE](../../../Framework/docs/KNOWLEDGE-IDE.md); [HOW-WE-BUILD](../HOW-WE-BUILD.md)).

**Reach.** At start, load the office rules, module's *current state*, open board commitments, complete handover, and a compact map of topics and record counts. Before work, derive the task's entities, paths and likely failure modes. A local C#/SQL retriever searches exact identifiers and paths, lexical terms and aliases, then expands through dependencies, superseded records, contradictions and office lessons. Return a ranked *candidate list with IDs, why matched, freshness and coverage count*; read full bodies for the candidates and their linked counterevidence. If recall is thin, broaden the query and inspect neighboring topics. A zero-match or one-word match is a reason to broaden, not a passing gate. A read acknowledgement records IDs and source versions actually delivered, not a self-reported sentence. Keep the complete index queryable, but do not inject every entry at every start. The current full-pages gate can pass after reading an irrelevant “wastewater” note; its own limitations document this ([START-FULL-MEMORY](../../../Framework/docs/START-FULL-MEMORY.md)).

**Carry.** A conversation carries Ian's question, current decisions, unresolved questions and references to evidence; completed searches become short cited findings. A worker carries goal, done-when, budget, owned module, relevant bodies, current code and test evidence; it can expand retrieval without a fixed quota. A helper receives a narrow question and returns findings with source IDs and uncertainty, rather than forwarding pages. A reviewer starts from the requirement, diff, relevant counterevidence and independent checks, and must search for missed hazards before agreeing. Helpers and reviewers need their own retrieval path: the proposed start gate does not cover subagents ([START-FULL-MEMORY](../../../Framework/docs/START-FULL-MEMORY.md)). Subagents have separate contexts but consume the same usage pool ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)).

**As context grows,** externalize decisions and the next action at milestones; keep a live, source-linked handover before compaction or restart. Preserve the approved 850k stop unless measured evidence justifies changing it. On the reported 900k window, a handover begun at 850k can itself run into compaction; the 300k warning must therefore prompt a real state save, and the save must be verified before relying on it ([G5-CONTEXT-STOPS](../../../Framework/docs/G5-CONTEXT-STOPS.md)). Claude Code reloads much startup material after compaction; it does not make discarded dialogue a trustworthy permanent memory ([context window](https://code.claude.com/docs/en/context-window)).

## IQ risk and a test that can fail

The failure is *missing a decisive record* because a task uses an unindexed synonym, spans modules, or cites a superseded source. Before changing the startup path, freeze a blinded set of real cold-start tasks across all six repos: direct, paraphrased, cross-module, conflicting and “no relevant record” cases, plus the five handover questions. Humans label required record IDs, prohibited stale IDs and expected decisions. Run today's installed path and the proposed retrieval path with the same model and task, score whether each finds the required bodies, cites current sources, answers correctly, catches contradictions and completes the task. Repeat with the proposed full-pages path as a comparator. **Fail the pilot on any missed safety-critical record or worsened task decision;** require noncritical recall and task quality at least equal to the best comparator, then compare token counts and time. The existing six-of-six cold proof tests delivery under its own questions; it does not establish retrieval recall on unfamiliar work.

## Savings and build cost

The source table reports Operations at 80,376 startup tokens today and a *projected* 160,043 after full pages: **79,667 extra per request**, or **7,966,700 raw tokens over 100 requests** (100 × 79,667), before any bodies ([START-FULL-MEMORY](../../../Framework/docs/START-FULL-MEMORY.md)). Avoiding that pending addition avoids that amount *relative to the pending design*; it is **not a measured saving against today's installed system**. Actual net savings from a smaller start plus retrieval calls, cache writes, output, restarts and task duration are unmeasured. The brief's 3,785 million raw versus 110 million new tokens implies about 97.1% of counted raw tokens were cache reads (calculation: 1 − 110/3,785); this is why raw-token reduction cannot be equated to allowance or dollars. Claude Code manages prompt caching, and its subscription usage display is distinct from API-list-price cost ([prompt caching](https://code.claude.com/docs/en/prompt-caching); [costs](https://code.claude.com/docs/en/costs)). The allowance formula is unknown.

Build the smallest read-only pilot in the existing C#/SQL `kor`: manifest, exact/lexical/alias retrieval, linked-record expansion and a replayable coverage report. No new store and no memory migration. Use the frozen tasks and token logs to decide whether richer local ranking is worth building. Only after that proof consider changing hooks. The engineering estimate in hours is **not measured**; the bounded first piece is one retriever, one corpus manifest and one paired evaluation, with no Drafter run.

## Alternatives rejected

1. **Full one-line pages plus a subject gate** deserves serious consideration: the cold tests improved from zero to six of six in each repo. It also adds 23k–80k tokens to every request, can accept an irrelevant match, and does not cover changed subjects or subagents. Keep it as the comparator and fallback if retrieval fails the IQ test.
2. **Every memory body at session start** gives literal completeness of delivery, but Operations alone is estimated beyond the context window; repeated input would crowd out work and provoke compaction. Completeness of delivery also does not prove correct use.
3. **Only CLAUDE.md/auto memory/skills** is cheap to operate but cannot serve as KOR's authoritative, versioned cross-module record. Claude Code auto memory loads only its first 200 lines or 25KB and topic bodies are on demand; skills load their full text when invoked ([memory](https://code.claude.com/docs/en/memory); [skills](https://code.claude.com/docs/en/skills)). They can carry routing instructions, not replace the brain.

## Critique of OverLORD's sealed first draft (read after the independent answer)

**What it gets right:** external memory, role-specific context, small starts, bounded helper outputs and allowance uncertainty. Its reviewer share checks: 38.8M / 110M new tokens = 35.3%. Redirect effort to product work once a memory change passes a quality gate.

**What breaks:** the 150k/400k/40k lines are unproven quality thresholds. Operations starts at about 80k tokens today; full pages project 160k, already above the conversation line. A 40k reviewer cannot receive today's start without changed wiring. Drafter work may need over 400k; some conversations need much less than 150k. Use task phase and handover readiness. “Everything on its subject” fails with synonyms, cross-module dependencies, conflicts and a mischosen subject. A source hash detects change; it does not make a record “always current.”

The **49% raw-token saving is a context-clipping counterfactual**: it assumes work, retries, handovers and request count stay constant. It cannot establish allowance savings. Its cold test can pass while a task misses a decisive record; add blinded task and retrieval tests. Review per piece may reduce duplicate reads, but removing per-commit coverage needs a cumulative diff and integration gate. The draft misses the gate's subagent and subject loopholes, source-linked retrieval, and the 850k handover/compaction race.
