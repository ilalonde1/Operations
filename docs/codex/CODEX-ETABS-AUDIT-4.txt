RULES OF EVIDENCE

  1. The report, the documents, the workbook and the test suite are claims made by the thing
     under audit. None is evidence. Measure the artifact.

  2. Read the shipped PDFs as text, not the HTML they were built from. A document is what lands
     in the engineer's folder, not what the source says it should be.

  3. Objects named "K" followed by a letter and digits were written by this tool, and some files
     in the two job folders are its own output round-tripped through ETABS. Establish provenance
     before using any file as ground truth.

  4. A check is not proved by passing. It is proved by failing on the defect it exists for. If
     you cannot make one fail deliberately, say so — that check is decoration.

  5. State the file and the numbers behind every finding. A defect read off code is not a finding
     until you say what it does to a model an engineer opens.

  6. Where you cannot determine something, say so and say what would settle it.

WHAT I WANT TESTED

  Questions, not a list of suspected faults. Answer them with measurements, and do not stop at
  the edge of this list.

  1. THE WORKBOOK SAYS EVERY JUDGEMENT IS SETTLED. Is it, and is each stated reason true?
     Generate it for both jobs. Row by row: does the value it says was used match the value the
     run actually used on that job? Does the evidence describe something really present in the
     model or the drawings it names? Does any row state a fact about one job inside the other
     job's workbook? A row marked DECIDED with a wrong reason is worse than an open question,
     because nobody re-checks it.

  2. DOES AN OVERRIDE ACTUALLY OVERRIDE? Prove it end to end with a rule that has never been
     driven through this path before — not one that already has a test:

       generate the workbook → answer a row written as already decided → dxf-import-rules →
       regenerate → confirm the geometry moved the way the answer demands → restore → confirm it
       moves back

     Then try to break it: a malformed answer, a row binding several settings answered with one
     number, two rows writing the same setting, an answer typed into a hidden column, the import
     run twice. For each, say which happens — silently ignored, silently half-applied, or refused
     with a reason the engineer can act on.

     This writes real rows to KorStandards.analysis. That is the mechanism working as designed.
     Say exactly what you wrote, and leave the database holding the values it started with.

  3. IS EVERY RULE THE TOOL RUNS ON VISIBLE, AND DOES THE DATABASE AGREE WITH THE CODE? Keys,
     values, units, confidence. Any rule the code applies that KorStandards does not hold, or
     holds and the code ignores. Whether migration 039 is idempotent and whether the live
     database matches what a clean run of that file would produce.

  4. DO THE DOCUMENTS SAY ONLY THINGS TRUE OF THE MODELS SHIPPING BESIDE THEM? Every count,
     storey name and claim about behaviour, in the dossier, the one-pager and the per-job
     summary. Then the harder question: what does a document assert that no automated check could
     ever catch, and is it true?

  5. THE PUBLISH GATE. It exists to stop a stale or wrong document reaching an engineer. Make it
     fail on purpose several ways — a count one out, a true claim phrased so no pattern sees it,
     a document shipped beside a job it does not describe. Where it does not catch something, say
     what phrasing gets through.

  6. IF I HAND IT A THIRD JOB TOMORROW, WHAT DOES THE ENGINEER GET AND WHAT IS WRONG WITH IT?
     Answer concretely. Values, prose, folder-layout assumptions, sheet naming, layer names,
     allowlists — anything that only makes sense for 31168 and 31138.

  7. ANYTHING THAT LEAVES THE MODEL WITHOUT APPEARING IN THE REPORT. Read and dropped, skipped,
     deduplicated, or fallen back on, where no count moves and no flag is raised. This class has
     cost more here than every other combined, and each instance passed a green suite.
