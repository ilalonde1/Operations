## Critical issues

### C1 — Active project intel is still stranded on retired MPIs

**File/Table:** `opportunities.IntelProject*`, `opportunities.MajorProjectEnrichment`, `opportunities.MajorProjectsInventory`

**Problem:** The live graph still has active child intelligence attached to retired project rows. This is the exact prior-audit lifecycle problem, and it has worsened in the IntelProject tables.

**Evidence:** Live SQL:

| Table | Active rows joined to retired MPI |
|---|---:|
| `IntelProjectAction` | 246 |
| `IntelProjectSignal` | 262 |
| `IntelProjectRisk` | 221 |
| `IntelProjectKeyPerson` | 149 |
| `MajorProjectEnrichment` | 1,820 |
| `IntelWork` | 0 |
| `CrmEngagementProjectLink` | 0 |

Sample rows: `IntelProjectAction` ids 550-552 point to retired MPI 60
`'Vista' Thermal Coal Mine`, retired by migration 180 as out-of-lane; ids
254-258 point to retired MPI 221 `Coliseum LRT / Expo Centre Pedway`, retired
by migration 177 as duplicate. `MajorProjectEnrichment` ids 274/2195 point to
retired MPI 21, retired by migration 118 as DEAD.

Prior audit baseline was 331 active IntelProject* rows on retired MPIs; current
count is 878. That is a regression.

**Why critical:** The AI/Deltek phase will rely on project intelligence as a
fact graph. Today, some intelligence is attached to rows every active-set query
correctly hides. That means the same project can appear empty in active views
while its intel exists on a retired sibling, and out-of-lane/dead project intel
can remain queryable if a path skips the active MPI join.

**Recommended fix:** Define one lifecycle rule and enforce it: on project
dedup, repoint child intel/enrichment/link rows to the survivor where no unique
collision exists; on true lifecycle retirement, retire child intel/enrichment
with the parent. Add a post-migration assertion query that must return zero for
each child table above before any migration retiring MPIs is accepted.

## Major issues

### M1 — MPI structural/GC canonical columns are not real FKs and already point at retired org artifacts

**File/Table:** `opportunities.MajorProjectsInventory.StructuralEngineerCanonicalOrgId`, `GeneralContractorCanonicalOrgId`

**Problem:** `StructuralEngineerCanonicalOrgId` and `GeneralContractorCanonicalOrgId` are canonical-org IDs in practice, and the dedup CLI repoints them, but the database does not enforce them as FKs.

**Evidence:** Migration 46 adds both columns as plain `bigint` (`Kor.Opportunities.Data/Schema/46_MpiTeamColumns.sql:16-23`) and only adds indexes (`:26-31`). Live `sys.foreign_keys` lists `MPI.ProponentCanonicalOrgId` and `MPI.ArchitectCanonicalOrgId`, but the query for FK rows on `StructuralEngineerCanonicalOrgId` / `GeneralContractorCanonicalOrgId` returns both columns with blank `FkName`.

Live SQL shows active MPIs with those columns pointing at retired orgs:

| Role | Count |
|---|---:|
| `StructuralEngineerCanonicalOrgId` -> retired org | 12 |
| `GeneralContractorCanonicalOrgId` -> retired org | 7 |

Examples include MPI 2218 `Burnaby Hospital Renewal` -> retired org 69853
`Glotman Simpson ...; Stantec ...; Fast+Epp ...` and MPI 5968 `The Butterfly +
First Baptist Church Complex` -> retired org 70930 `Icon West Construction
(new); Haebler Group (heritage)`.

The CLI knows about these columns (`tools/BdCanonicalDedup/Program.cs:65-68`),
but direct SQL migrations/imports can bypass that protection.

**Why major:** These fields drive incumbent-SE, displacement, differentiator,
and open-seat logic. A partner seeing a retired composite string as a real
structural engineer or GC is a trust hit.

**Recommended fix:** Clean the 19 live rows, then add nullable FK constraints
for both columns to `CanonicalOrg(Id)`. If existing dirty historical rows block
that, that is exactly the data gate to close.

### M2 — `vOpenSeatPursuit` still has no stage or `SeatStatus` gate

**File/Table:** `opportunities.vOpenSeatPursuit`

**Problem:** The view defines an "open seat" as active MPI + no structural
engineer ID/name. It does not require early stage and does not require
`SeatStatus='likely-open'`.

**Evidence:** `Kor.Opportunities.Data/Schema/158_BdLeverageViews.sql:72-92`
creates `vOpenSeatPursuit`; the `WHERE` clause is only `m.RetiredAtUtc IS NULL`,
`m.StructuralEngineerCanonicalOrgId IS NULL`, and blank `StructuralEngineerName`.

Live SQL joined the view back to MPI and returned 11 CA late/dead rows, including:

| MPI | Project | Stage |
|---:|---|---|
| 8290 | The Lindley | `DELIVERED Mar 2025` |
| 8304 | 820 Olive | `DELIVERED 2019` |
| 8306 | Olympic + Hill | `DELIVERED 2025` |
| 8342 | 30 Van Ness | `ON HOLD since Aug 2023; 47-story` |
| 8357 | 42XX Marina del Rey campus | `DELIVERED Oct 2024` |

The current dashboard `OpenSeatCount` does **not** include those rows because it
uses `SeatStatus='likely-open'`; live SQL found zero CA late/dead rows with
`SeatStatus='likely-open'`. The stale view is the remaining hazard.

**Why major:** `vOpenSeatPursuit` is explicitly documented as a reusable ranked
seat view (`158_BdLeverageViews.sql:11-12`). If Arc-7 tools or Deltek fusion
reuse it, they will revive a known false-positive class: "SE unnamed in press"
does not mean "open seat."

**Recommended fix:** Change the view to require `SeatStatus='likely-open'` and
an early-stage allowlist. Keep delivered/on-hold portfolio rows out of pursuit
views unless a separate historical-reference view is intentionally queried.

### M3 — BD dashboard bid-window KPI is 63 rows lower than the UI-equivalent method

**File/Table:** `Kor.Opportunities.Data/MajorProjects/SqlBdDashboardStore.cs`, `Kor.Operations.App/Opportunities/MajorProjectsInventoryViewModel.cs`

**Problem:** The dashboard store counts bid-window rows using `Stage` only. The
WPF major-projects funnel helper checks `Stage`, `ProjectStage`, and
`ProjectStatus`.

**Evidence:** Store SQL uses only `Stage LIKE ...` at
`SqlBdDashboardStore.cs:154-162`. The UI helper explicitly loops all three
fields at `MajorProjectsInventoryViewModel.cs:416-430`. Live SQL using the same
sector basket returns:

| Method | Count |
|---|---:|
| Store/current dashboard | 196 |
| UI-equivalent all-three-field method | 259 |
| Drift rows | 63 |

Sample missed rows: MPI 2380 `The Education Learning Centre` has
`Stage=Planned`, `ProjectStage=Procurement`; MPI 3272 `Garden Street 30-storey
tower` has `Stage=Planned`, `ProjectStage=Procurement`, `ProjectStatus=Under Review`.

**Why major:** This is KPI methodology drift in the dashboard layer. It will
teach AI and partners a lower "in bid window" number than the actual funnel UI.

**Recommended fix:** Share one SQL predicate/helper for bid-window classification
and update the metric definition text to match the implementation.

### M4 — CRM region vocabulary is not enforced, and two live rows are invalid

**File/Table:** `opportunities.CrmEngagements.Region`, `SqlCrmEngagementStore`

**Problem:** CRM duplicate prevention is now good, but region values are free
text. The UI region tabs expect `VancouverIsland`; two live rows have
`Vancouver Island`.

**Evidence:** Live SQL:

| Id | Buyer | OwnerStaffId | Region |
|---:|---|---|---|
| 95 | Emerge Modular | Rory | `Vancouver Island` |
| 97 | Evantra Developments | Rory | `Vancouver Island` |

The UI options are hard-coded at `Kor.Operations.App/Crm/BdTrackingViewModel.cs:30-39`.
Filtering compares exact string equality at `BdTrackingViewModel.cs:112-118`.
`SqlCrmEngagementStore` binds whatever string is supplied (`SqlCrmEngagementStore.cs:237-255`).
Live constraints on `CrmEngagements` include `CK_CrmEngagements_Stage` and the
unique indexes, but no region CHECK constraint.

**Why major:** These two engagements disappear under the Vancouver Island tab
and remain visible only under "All Regions." This is exactly the kind of
small-looking CRM defect partners interpret as "the system lost my relationship."

**Recommended fix:** Normalize the two rows, add a `CK_CrmEngagements_Region`
constraint for the six allowed values, and centralize region constants so import,
store, UI, and migrations cannot drift.

### Mi2 — Migration hygiene is inconsistent after 137

**File/Table:** `Kor.Opportunities.Data/Schema/137..182`, `231..233`, `244`

**Evidence:** Static scan of migrations 115-257 found the early 115-136 batch
mostly used `SET XACT_ABORT ON` + transaction, but many data-changing migrations
137-182 do not. Example: migration 137 retires hundreds of org IDs with no
explicit transaction or `XACT_ABORT` (`137_JvArtifactRetireAndPlaceholderSuppress.sql:1-80`).
Migration 221 is the better pattern: it uses `SET XACT_ABORT ON`, `BEGIN TRAN`,
mass updates, `COMMIT TRAN`.

**Why minor:** The applied production state exists, but replay/scratch safety is
weaker than the prior audit's stated discipline.

**Recommended fix:** Restore the convention for every data-changing migration:
`SET XACT_ABORT ON`, explicit transaction, preflight guards, post-change verify
SELECT/THROW.

**Evidence:** File line count is 2,758. `tools/BdCanonicalDedup/Program.cs:246-253`

## Architectural concerns

- **Soft-retire is still not referentially disciplined.** C1 and M1 are the same
  root problem in two places: retiring a parent row does not define what happens
  to every child/role edge.
- **`IntelPerson` identity is improved but still has a weak last-resort fallback.**
  `IntelNaturalKey.ComputePerson` now keys by email, then LinkedIn, then
  normalized name + org (`IntelNaturalKey.cs:15-35`), and migration 255 backfilled
  it. If a person has no email, no LinkedIn, and no current affiliation in the
  same draft, it still falls back to normalized name only.
- **CA research rows mix portfolio evidence and pursuit inventory.** Active CA
  MPI rows include delivered/on-hold portfolio evidence. That is fine if
  explicitly modeled, but dangerous if generic "active MPI" means pursuit.
- **The DB has no migration tracking table.** Live query for migration tracking
  tables under `opportunities` returned no rows, so replay/order verification is
  still external to the database.

  deleted verified duplicate engagements (`251_BdTrackingCrmEngagementDedup.sql:26-104`);
  migration 252 adds `UX_CrmEngagements_BdRelationship` on

  Live exact-key duplicate query returned no rows.

  LinkedIn, then name+org (`IntelNaturalKey.cs:15-35`), and migration 255
  backfilled active rows with collision handling (`255_IntelPersonIdentityAnchorNaturalKey.sql:8-27`, `:229-240`).
  Live active duplicate `NormalizedName` query returned no rows.
- **Dedup automation is safer than on 2026-06-09.** The worker job is retired/no-op
  (`CanonicalOrgDedupJob.cs:49-63`), the CLI has session and transaction app locks
  (`Program.cs:819-841`), and the FK target list is explicit (`Program.cs:60-108`).
- **CA permit intake is now guarded at source and in code.** Config filters were
  added in migrations 254/256; the provider also rejects terminal permit stages
  in code (`CaSocrataMajorProjectsInventoryProvider.cs:469-473`, `:841-855`).
  Live SF active statuses are only filed/approved/reinstated/filing/triage.
- **BD/CRM AI context wiring is broadly in place.** The CRM and BD windows/VMs

## Foundation verdict

Not clean enough yet to make the BD foundation load-bearing for Arc-7 AI tools,
Deltek-BD fusion, or scale. The original 2026-06-19 blockers were mostly fixed,
but three current gates must close first: **C1** zero active project intel and
enrichment on retired MPIs (`IntelProject*`, `MajorProjectEnrichment`),
**M1** enforce/clean MPI structural-engineer and GC canonical FK discipline
(`MajorProjectsInventory.StructuralEngineerCanonicalOrgId`,
`GeneralContractorCanonicalOrgId`), and **M2/M3** align pursuit/KPI methodology
(`vOpenSeatPursuit`, `SqlBdDashboardStore`). Until those are closed, the module
is much improved but still not a solid foundation for AI or Deltek fusion.
